# Pokémon Brilliant Diamond — PC rebuild

A Unity project that rebuilds Pokémon Brilliant Diamond (Nintendo Switch, v1.3.0) as a native Windows game, from a dump of
your own copy of the game. The game code is restored from the shipped IL2CPP binary; assets come from the shipped data and
are exported from your dump, never committed.

## Where the code comes from

This repository's code was produced without any third-party reconstruction project:

- **Declarations** (`Assets/Scripts/{Game,AssetAssistant,DebugLog,nn,DOTweenPro}`, one file per type at
  `<Assembly>/<namespace>/<Type>.cs`) are generated by `tools/clean/skelgen` from our own Il2CppDumper dump of the game's
  metadata; attribute arguments are decoded from the game's own attribute generator functions (`tools/clean/attr_decode.py`).
- **Method bodies** are translated from the decompiled game binary (Ghidra + our cleaner), by this workspace's own
  restoration campaign, by a deterministic pass over exact instruction shapes, or by clean-room translators that work
  only from the binary.
- `Assets/Scripts/_Ours/PcPlatform` is this workspace's own platform layer (PC input, display, saves, keyboard, frame clock).
- `Assets/Editor` is this workspace's editor tooling (Windows build, audits, probes, the editor asset loader).
- Vendor files: `Assets/Plugins/DOTween` (Demigiant DOTween 1.2.335, the shipped version) and `Assets/Wwise` (Audiokinetic
  Wwise Unity Integration 2019.2.4).

Player settings follow the shipped game (`productName` `Dpr`, `companyName` `DefaultCompany`, the shipped Graphics / Quality
settings). The shipped code paths are kept: Switch-only code sits under `#if SWITCH`, and where the PC build changes a shipped
statement (the unlocked frame rate, `PC_UNLOCKED_FPS`) the shipped statement stays in the `#else` arm.

## Requirements

- Unity **2019.4.27f1** (the version the game was built with) with Windows Build Support (IL2CPP).
- Visual Studio Build Tools with the C++ workload (IL2CPP compiles the game to native code).
- Your own dump of the game; the setup and all working notes are in `../HANDOFF.md` of the workspace.

## Playing in the editor

Open `Assets/Scenes/level0.unity` and press Play. In the editor the game loads its assets straight from the project
(`StartupSettings` target AssetDatabase).

## Building for Windows

Menu **BDSP > Windows Build** (or `-executeMethod BdspWinBuild.WinBuild.<step>`):

1. *Check* — verifies the bundle plan against the shipped manifest.
2. *Build AssetBundles - FULL* — all 13,651 bundles plus the Windows asset manifest (`Dpr.bin`).
3. *Build player - DEVELOPMENT / RELEASE* — the IL2CPP player in `build/win64_<time>/Dpr.exe`, with the bundles linked in.

Each step restores every setting it changes; reports go to `work/winbuild/reports/`. With the environment variable
`BDSP_BUILD_FLAVOUR=<name>` the bundles, manifest and player go to `build/bundles_win64_<name>`, `build/manifest_win64_<name>`
and `build/win64_<name>_<time>` instead, so a rebuild never rewrites bundle files an existing player folder hard-links.

## PC options

The in-game Options menu starts with four PC rows: **Display Mode** (Windowed / Borderless Window / Full Screen),
**Resolution**, **Frame Rate** (30 FPS = the original pace, up to Unlimited) and **V-Sync**. They are stored in
`pc_settings.ini`, not in the save data.

## Where things are stored

`%USERPROFILE%\AppData\LocalLow\DefaultCompany\Dpr\`

- `nn\save\...\SaveData.bin` / `Backup.bin` — the save, in the shipped format
- `pc_settings.ini` — the PC options
- `Player.log` — the player's log

## Controls (keyboard)

Z = A, X = B, C = X (menu), V = Y, E = L, U = R, Q = ZL, O = ZR, `=` = +, `-` = −, arrow keys = D-pad, WASD = left stick,
IJKL = right stick (`_Ours/PcPlatform/PcHid.cs`); an XInput gamepad works too.
